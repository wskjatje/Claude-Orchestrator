# 本地 / 云双模型工程化优化方案（项目复核定稿）

**复核日期：** 2026-11-10  
**依据：** 附件《本地 / 云双模型工程化优化方案 · 定稿 v1.0》及当前工作区源码、脚本清单。  
**目的：** 将附件中的历史诊断改成基于当前仓库状态的可执行方案。本文不把附件中的提示、命令或验收数值视为已验证事实。

## 1. 结论

项目仍有明显优化空间，建议继续推进双模型工程化，但不应照附件 T00–T21 原样全量开工。附件数据注明来自 2026-11-05 的 Ollama 0.40.14 / qwen2.5-coder:14b 实机观察；它适合作为问题线索，不能代表 11 月 10 日当前运行表现。

当前代码已经有不少附件所提能力：本地编排环接入 MCP；上下文压缩会归档旧轮次；前端会读取并注入项目规则；云端直聊已有 SSE 流式实现；Host 环有停止状态、工具执行事件和回合日志等基础。因此，重新实现这些功能会重复投入。

仍然成立的核心架构问题是**两套执行环能力不一致**：`server/host-agent-loop.mjs` 是面向云端 OpenAI 兼容接口与 Ollama 的 Host 工具环，内置 8 类工具但不含 MCP；`server/vendor/cad/local-mcp-orchestrator.js` 则负责本地模型与 MCP，另有各自的协议解析、上下文及流式逻辑。优化应先建立实测基线，再统一共享的模型能力、工具权限与评测契约，逐步收敛两条路径。

## 3. 优化目标与原则

目标是同一套任务契约在本地和云通道上可预测地完成：**发现代码 → 读取 → 修改 → 验证 → 交付**，并且用户能看见当前模型、工具权限、失败原因和恢复路径。

1. 先建立可复现评测和日志，再以数据决定实现优先级。
2. 共享能力与权限契约，执行环逐步迁移；避免新建第三条 Agent 执行环。
3. 按模型声明能力（工具调用、上下文窗口、视觉、流式），未知即标为未知，不用模型名猜测。
4. 工具与写入一律受现有 Ask / Plan / Agent 权限约束；文本 JSON 仅作为显式协议降级，必须经过工具白名单、参数 schema 和权限检查。
5. 自动路由或故障转移不得静默换模型；明确告知用户实际执行模型及是否产生费用。
6. 每项改进都要能回滚并有行为级验收；估算在基线和代码切片后再更新。

## 4. 最终实施计划

### 阶段 0：基线与需求冻结（建议 1–2 人日）

- 将附件 12 个任务整理成隔离工作区评测；覆盖读码、单文件/多文件编辑、测试修复、大文件、规则、MCP、中断恢复、Ask 越权拒绝。
- 对至少一个本地模型及每个拟支持的云供应商分别重复运行；记录通过判据、模型 ID / digest、服务版本、工具轨迹、窗口、首 token / 总耗时、重试、编辑失败、token / 费用。
- 分别运行 Host 环和 local-MCP 环同一组可比任务，标注能力差异；先人工审阅评分准则，避免把模型输出文本当作成功证据。
- 新建版本化基线报告。附件的估算值保留为历史参照，不用作当前基线。

**出口条件：** 每个任务有机器可检验断言或明确人工判分项；本地与云端都能生成可比较报告；失败类别可定位。

### 阶段 1：窗口、协议、请求控制（建议 3–5 人日）

- 给 Ollama 能力解析增加实际生效窗口来源、模型 digest 和缓存失效；请求的 `num_ctx` 不超过已知模型上限与用户资源上限，未知能力明确显示并用保守值。用 `/api/ps` 和连续读文件任务验证。
- 提取共享的工具调用归一层：原生 `tool_calls` 优先；仅对声明不兼容的模型尝试受控 JSON 协议；校验工具名、参数 schema、重复调用及正文误识别。保留原始响应和所选协议用于诊断。
- 让 Host 环模型请求接受统一流式事件和请求级 AbortController；取消传入 fetch、Ollama、MCP 调用和子进程。增加 429 / 5xx 分类与有限退避，尊重 `Retry-After`，不重试权限错误或不确定副作用的写操作。
- 删除本地流式去重逻辑前先加专门回归样例；只有复现丢字时才针对对应路径修正。

**出口条件：** 4k / 8k / 更大窗口配置均无静默截断；不支持 tools 的模型给出可操作错误或走安全降级；停止模型请求和命令均在明确时限内生效；普通文本不能触发工具。

### 阶段 2：执行环能力收敛（建议 4–6 人日）

- 定义共享的 `ModelAdapter`、模型能力记录、工具 schema、统一事件、错误分类和权限接口；首步仅适配，不改变现有路由行为。
- 将 MCP 的发现、schema 裁剪、超时、调用审计接入共享工具注册表；保留现有 local-MCP 路径作为回退，逐供应商验证云通道。按上下文预算限制工具描述数量，并为被裁剪工具提供可发现目录 / describe 机制。
- 补齐 Anthropic / Gemini 原生协议适配，或明确当前版本暂不支持其 Agent 工具环；模型选择器应显示“聊天可用 / 工具可用 / 本地 / 云端”等真实能力，不以一个开关混淆通道。
- 采用按能力灰度：内部评测通过后逐步将流量迁移到共享路径；保留单一回退开关和版本化诊断日志，移除旧路径前要求基线不退化。

**出口条件：** 本地与云执行同一权限规则；选定供应商通过至少一次读→改→测；MCP 工具调用受权限、超时和审计约束；失败时不静默切换模型。

### 阶段 3：写入可靠性与上下文质量（建议 4–6 人日）

- `read_file` 增加 `offset/limit` 或行号区间，返回路径、范围、总行数、截断状态和下一页位置；默认字符数由模型剩余预算计算，不继续用固定 16k。
- 统一所有 Agent 写盘入口：检查路径穿越、写前文件指纹、写到临时文件后原子替换、写后校验；文件已被外部修改时返回冲突，不覆盖。
- 修正 120k diff 空白化：大文件以 hunk / patch 存储与展示；快照记录哈希，支持按回合撤销。检查当前 Plan 暂存、Accept 流程和工作区写入的 checkpoint 是否覆盖 Host Agent 直接写盘，避免只修 UI 路径。
- 在已有规则注入和 compact 上增加路径优先级、token 预算、任务状态卡（目标 / 已完成 / 待完成 / 验证 / 风险），压缩事件可追溯原文归档。

**出口条件：** 冲突不会覆盖用户改动；100k+ 文件的局部编辑仍可审阅及回滚；4k 窗口多文件读取可分页；压缩前后任务状态可恢复。

### 阶段 4：任务规划、模型路由与发布治理（建议 3–5 人日）

- 增加结构化计划事件和任务步骤状态，先服务于 UI 透明度；按评测数据决定是否对长任务强制规划，不预先抬高所有任务轮数上限。
- 做可解释路由：用户可锁定本地 / 云；自动选择仅在用户允许时启用，展示所选模型、原因、费用上限；超限先停并报告，不静默降级。
- 将 12 项评测及关键权限 / 编辑回归加入 nightly 或发版候选流程；使用至少 3 次重复运行计算通过率与波动，低置信度或模型服务不可用时标记“未测”，不计为通过。
- 发布采用内部灰度 → 本地通道 → 单云供应商 → 其他云供应商；每阶段保存评测报告及回滚版本。

**发布门槛：** 所有通道达到评测中预先登记的目标；连续 3 次结果波动在约定范围内；无越权写入、静默换模型、不可恢复写入或伪造测试结果。具体数值须由阶段 0 基线共同确定，不沿用附件中未经当前复测的 10/12、12/12、2 秒等目标。

## 5. 优先级与建议排期

| 优先级 | 交付 | 排序理由 |
|---|---|---|
| P0 | 当前双环对照评测、模型窗口实测、统一失败记录 | 先区分真实缺陷和已修复项，防止重复开发。 |
| P1 | 窗口协商、共享工具协议、可中断请求、MCP / 权限契约 | 直接决定本地/云能否完成工作并避免安全退化。 |
| P1 | 原子写、冲突检测、大文件 diff / 回滚、行区间读取 | 直接降低数据损坏与编辑失败成本。 |
| P2 | Host 环流式、云供应商原生 tools 覆盖、规则/compact 观测 | 提升跨通道一致性与复杂任务稳定度。 |
| P3 | 自动模型路由、动态轮次、计划面板、成本策略优化 | 依赖可靠度量；应在前述能力稳定后推进。 |

附件估算的 17–22 人日可暂作为**未复核范围**，但现有代码复用较多、又有供应商方言和灰度集成工作；推荐先完成阶段 0，再按实际差异拆卡、估时。不要直接承诺 5–6 周或阶段通过率。

## 6. 暂不重复建设的内容

- 不从零新增 MCP 客户端或项目规则注入；先提取和复用 local-MCP 及现有规则发现路径。
- 不从零实现会话压缩；为已有压缩添加任务状态卡和行为评测。
- 不把“所有云模型支持 Agent tools”作为既成事实；逐供应商验证方言与工具能力。
- 不直接增加模型轮数或启用自动路由；以评测证明必要性并保留用户锁定选项。
- 不把附件复现步骤中的本机 Ollama 请求、测量数据当作已在本轮执行；运行时数据须在目标机器重新采集。

## 7. 下一步交付顺序

1. 从附件 12 个任务建立仓库快照评测及评分规则。
2. 分别对 local-MCP 与 Host Agent 两条环跑相同本地模型任务，并对可用云供应商跑对应子集。
3. 输出“通过 / 失败 / 未测”基线和能力矩阵；确认当前 `num_ctx` 的请求值与运行时加载值。
4. 依据基线决定窗口 / 协议 / 取消 / 写入回滚的具体改造范围与人日，再开始实现。

**本轮结论：** 项目值得优化；优先修正双执行环能力漂移与可观测性，再做写入可靠性。附件整体方向仍有价值，但部分诊断已过时、若干估算没有当前证据，需以本方案的复测基线替代。
