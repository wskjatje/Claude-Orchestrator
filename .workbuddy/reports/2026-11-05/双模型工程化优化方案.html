摘要：三个数字说清问题

上一轮已确认 4 个 P0（流式丢字、云模型不可选、云模型无工具环、只读意图编造答案）。本轮继续深挖后可以给出一个更强的结论：当前本地模型无法完成 Agent 任务，主因不是模型能力不足，而是执行内核在三个关键位置断链——上下文、工具协议、工具供给。三个数字足以定位：

4,096 tok
Ollama 实际加载的上下文窗口（未传 num_ctx）。应用侧按 32,768 计算预算与压缩阈值。
0 个
qwen2.5-coder:14b 返回的原生 tool_calls。工具调用被写在 content 文本里，Host 环完全不识别。
8 → 0
项目 .mcp.json 已配置 8 个 MCP 服务器，Host 执行环可用数量为 0。
一句话结论 现在不是"本地模型差点意思"，而是把 32k 窗口的模型硬塞进 4k 窗口、把工具调用当成普通文本、把 8 个 MCP 工具全部丢掉，再要求它像 Cursor 一样干活。这三处修完之前，换任何模型都不会有本质改善；修完之后，14B 级本地模型完成常规改码任务是可预期的。

一、真正的三层断链

断链 1 · 上下文层：预算按 32k 算，运行时只有 4k

model-capabilities.mjs 从 ollama show 读到 32768，前端据此设定压缩阈值（80% ≈ 26k），于是压缩永不触发；但 host-agent-loop 的 Ollama 请求体里没有任何 options，Ollama 按默认 4096 加载（已实测 /api/ps 返回 context_length: 4096）。

系统提示 788 字符 ≈ 246 tok 7 个工具 schema 3,605 字符 ≈ 1,127 tok read_file 默认一次读 16,000 字符 ≈ 5,000 tok ──────────────────────────────── 首轮 read_file 后理论占用 ≈ 6,400+ tok ＞ 4,096

也就是说：第一次读文件就已经溢出。Ollama 会从头部截断，最先被丢掉的正是系统约束和工具说明。模型随后表现出"忘记规则、重复读同一文件、改错位置、反复道歉"——这正是用户描述的"断断续续"。

断链 2 · 工具协议层：本地模型的工具调用根本进不了执行环

实测同一个请求，Ollama 返回的是文本而不是结构化调用：

$ curl .../api/chat (qwen2.5-coder:14b + read_file schema) has_tool_calls = False content = '{\n "name": "read_file",\n "arguments": { "path": "package.json" }\n}' tool_calls = null

而 host-agent-loop.mjs 的 extractToolCalls() 只读 message.tool_calls，拿不到就判定"模型没调工具"，于是连续两次"系统催促：必须调用工具"，最后以一段空话收尾。模型做对了，管道没接住。

更糟的是另一类模型（gemma 系、qwen2.5:32b）在带 tools 时直接被 Ollama 拒绝——真实日志里反复出现：

[turn] model=qwen2.5:32b ch=orch ... ms=78393 err=Ollama /api/chat HTTP 400: {"error":"Value looks like object, but can't find closing '}' symbol"} 已尝试精简改码工具集仍失败

注意：这恰恰是用户机器上最强的本地模型。也就是说"能力越强的模型反而更容易触发"，因为它在生成参数 JSON 时更"自由"。

断链 3 · 工具供给层：8 个 MCP 服务器对执行环完全不可见

项目 .mcp.json 配置了 filesystem / fetch / memory / external-apps / sequential-thinking / puppeteer / sqlite / sanshengliubu 共 8 个。但 Host 环的 TOOLS 是硬编码的 7 个内置工具，没有任何 MCP 合并逻辑；而且前端还有一道门禁，检测到启用了需 MCP 的服务器时直接禁止 Host 回落：

[turn] ... err=【MCP】已启用需 MCP 通道的服务器（filesystem、fetch、memory…）， CLI/本地编排失败后禁止静默 Host 回落（Host 无 MCP，禁止无证据兜底）。

web/src/lib/mcp-cli-gate.ts · 门禁实现

结果是一条死路：云模型没有 CLI，Host 又不许用；本地模型走 CLI 需要 Anthropic 登录，走 Host 则被门禁拦住。于是"启用了 MCP 的用户"实际上无法用任何非 Claude 模型完成带工具的任务——这解释了为什么体验会"时好时坏"，取决于你有没有开 MCP。

断链 4 · 执行保障层：没有流式、没有重试、没有真正的取消、没有检查点

  • 无流式：每一轮都是 stream:false，模型想 40 秒，界面就静 40 秒，然后整段蹦出。这就是"断断续续"的观感来源之一。
  • 无重试：全仓 host-agent-loop 内没有任何 429 / 5xx 退避逻辑。云端一个抖动就直接降级到本地模型，把任务状态交给一个更弱的模型继续做。
  • 无真取消：cancelState 只在轮次边界检查，chatOnce 的 AbortSignal.timeout(180s) 无法被用户中断。点"停止"后还要等当前请求跑完。
  • 无检查点：写盘后只保留 filePatches 的 before/after，且单文件超过 120,000 字符时直接置空——大文件改动无法回滚、无 diff 可看。

断链 5 · 上下文工程层：项目规则只"列出"不"注入"

project-rules.mjs 会扫描 .cursorrules、.cursor/rules/*.mdc、RULES.md、.claudecode/user-preferences.mdc，但唯一用途是给设置页展示与文件变更广播；从未进入 host-agent-loop 的 system prompt。同时也没有仓库地图、没有打开文件上下文、没有 @ 引用注入协议——现有 context 注入靠正则猜路径（expand-user-line-workspace-files.ts），猜不到就不给。

对照 Cursor：Rules 是强约束、Repo Map 是默认上下文、@ 是显式引用。这三件事直接决定了"改得对不对"，比模型参数量影响更大。

三、与 Cursor / Codex 的能力矩阵

"像 Cursor 一样做项目"拆开是 16 个可验证的能力点。现状与目标对照如下（"目标"= 本方案完成后的状态）：

能力点Cursor / Codex当前实现差距目标状态
工具调用协议原生 + 稳定仅原生；内容内嵌不识别致命原生 / 简化 schema / 文本 JSON 三层自动降级
上下文窗口协商按模型真实窗口假设值 ≠ 运行值致命请求前探测 + 显式 num_ctx，预算按真实窗口分配
MCP 工具全模型可用仅 Claude CLI致命内置 + MCP 统一注册，任何后端可用
云模型工具环原生纯文本直聊（上轮 P0）致命云模型走同一执行环
流式输出token 级整轮返回高文本与工具轮均流式

编辑精确度模糊匹配 + 补丁严格字符串匹配高精确 → 空白归一 → 行窗 → patch 四级回退

逐块接受/拒绝有写后审阅，>120k 无 diff中hunk 级 diff + 检查点回滚
后台进程终端常驻一次性命令中后台启动 / 读输出 / 终止
浏览器工具有仅 MCP puppeteer（且不可用）中内置浏览器暴露为工具
效果评测内部 benchmark静态字符串门禁致命真实任务集 + 成功率指标
一个容易被忽略的元问题 项目的 17 类门禁脚本全部通过，但真实链路有 5 处致命断链。原因是这些脚本检查的是"源码里有没有这段字符串"，而不是"任务能不能跑通"。所以本方案把端到端任务集列为 P0，而不是收尾工作——没有它，后面每一项优化都无法证明有效。

四、目标架构：统一执行内核

当前有两套并行的执行环：server/vendor/cad/local-mcp-orchestrator.js（有 MCP、仅本地）和 server/host-agent-loop.mjs（有云、无 MCP）。两套逻辑各自演化，直接导致了本轮发现的 400 错误处理、内容内嵌解析、流式去重三处不一致。正确做法不是再写第三套，而是合并为一套内核，差异下沉到适配器：

┌──────────────────────────────────────────────────────────────┐
│  Composer / Turn Policy（意图 · 模式 · 上下文级别）           │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  Agent Runtime（server/agent-runtime.mjs）—— 唯一执行环       │
│                                                              │
│  ① Model Adapter       openai │ anthropic │ gemini │ ollama  │
│  ② Tool Protocol       native │ simplified │ content-JSON    │
│  ③ Tool Registry       builtin(12) + MCP(n)  统一 schema     │
│  ④ Context Manager     真实窗口预算 · 规则 · 仓库地图 · 压缩  │
│  ⑤ Edit Engine         四级匹配 · 冲突检测 · 原子写 · 校验    │
│  ⑥ Verifier            test / typecheck / lint / 自愈重试     │
│  ⑦ Telemetry           turn 指标 · 成本 · 失败分类            │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
        workspace / MCP servers / PTY / LSP / browser
模块职责关键约束
Model Adapter把统一消息与工具 schema 翻译成各供应商方言能力（tools / vision / window）来自 model-capabilities，不猜
Tool Protocol决定"怎么把工具调用喂给模型、怎么把调用取回来"按模型缓存策略，失败一次即降级并记忆
Tool Registry内置工具 + MCP 工具统一注册、统一权限、统一超时工具数上限按窗口动态裁剪，避免 schema 挤占上下文
Context Manager预算分配（system / 工具 / 历史 / 工具结果 / 预留输出）预算以真实窗口为分母；压缩后保留"任务状态卡"
Edit Engine所有写盘唯一入口写前快照、写后校验、失败必回滚
Verifier按项目类型选择验证方式验证不通过不得声明完成

五、优化清单

P0 · 让"能干"成立（5 项，缺一不可）

C1 上下文窗口协商：按模型真实窗口下发 num_ctx

server/host-agent-loop.mjs · chatOnce() Ollama 分支 / shared/context-budget.mjs
问题
请求体无 options，Ollama 用 4096 默认值；应用按 32768 算预算。
改法
请求前读能力表拿到真实窗口，显式下发 num_ctx（取 min(窗口, 预算上限)）、num_predict、keep_alive；工具环温度降到 0.2。
验收
/api/ps 的 context_length 等于配置值；连续 3 次 read_file 后 prompt_eval_count 仍小于窗口的 80%。
// server/host-agent-loop.mjs · ollama 分支
const caps = await resolveModelCaps(backend.model)          // 已有实现，直接复用
const window = caps.contextLength || 8192
const budget = resolveLocalGenBudget({ forceDirectChat: mode === 'ask' })
const body = {
  model: backend.model, messages, tools: TOOLS, stream: false,
  keep_alive: '30m',                                        // 避免跨轮重载（冷启动 5–20s）
  options: {
    num_ctx: Math.min(window, budget.num_ctx || window),     // ← 关键
    num_predict: budget.num_predict,                         // ← 防跑飞撞 180s 超时
    temperature: 0.2, top_p: 0.9,                            // ← 工具调用稳定性
  },
}

C2 工具协议三层降级：原生 → 简化 schema → 文本 JSON

新增 shared/tool-call-protocol.mjs（从 vendor/cad/local-mcp-orchestrator.js:1411 提取）· host-agent-loop.mjs extractToolCalls()
问题
只读 message.tool_calls；qwen2.5-coder 把调用写进 content，qwen2.5:32b 直接 400。
改法
① 原生解析；② 空则从 content 提取 JSON（去围栏、平衡括号、容错尾逗号、支持一次多个）；③ 仍失败且模型历史上有 400 记录，改用"提示词内嵌工具协议"（system 里给 2 个示例，要求只输出 JSON）。策略按 model:digest 缓存。
验收
qwen2.5-coder:14b 能连续完成 read_file → search_replace → run_tests；qwen2.5:32b 不再报 400，自动走文本协议。

C3 MCP 接入执行环，并移除"启用 MCP 即禁止工具"的门禁

host-agent-loop.mjs（TOOLS 合并 + runTool 分发）· web/src/lib/mcp-cli-gate.ts
问题
8 个 MCP 服务器对执行环不可见；门禁把"无 MCP"当成硬约束。
改法
轮次开始时拉取已启用服务器的 listTools，统一转 OpenAI schema，命名 mcp__<server>__<tool>；执行时路由到 MCP client；按窗口裁剪数量（≤48，优先与任务相关者）。门禁改为"提示能力差异"而非"阻断"。
验收
本地模型与云模型都能调用 memory、fetch、sqlite；停用 MCP 时行为不变。

C4 云模型进入同一执行环（含流式与方言适配）

host-agent-loop.mjs · resolveChatBackend()

上轮已确认云模型走纯文本直聊；此外 Gemini 被显式排除（!isGemini），Anthropic 官方端点无对应适配。

P1 · 让"干得稳"成立（7 项）

C6 读文件带行号与区间

host-agent-loop.mjs · read_file
改法
schema 增加 offset / limit；返回带 行号│代码 前缀；默认读取量从 16,000 字符降到"窗口预算的 35%"（4k 窗口 ≈ 1,400 字符 / 约 60 行），并在结果里给出 nextOffset。
收益
模型能引用行号定位改动；单次读取不再撑爆窗口；大文件可分页读。

C7 编辑引擎四级回退 + 冲突检测 + 原子写

host-agent-loop.mjs · applySearchReplace() / persistWrite()
问题
严格字符串匹配，本地模型只要多一个空格就失败；且不校验文件是否在读取后被改动。
改法
① 精确匹配 → ② 空白/换行归一后匹配（替换时保留原缩进）→ ③ 首尾行锚点定位 → ④ unified patch；失败时返回"最接近的 3 个片段 + 行号"供模型自我修正。写前比对 mtime，变化则要求重读；写盘用 tmp+rename；写后跑语法校验（ts/js 用 tsc，py 用 py_compile）。
收益
本地模型 edit 失败率通常能从 30–40% 降到 10% 以下，这是"能不能连续工作"的分水岭。

C8 项目规则注入（.cursorrules / .cursor/rules / AGENTS.md）

project-rules.mjs（新增 buildRulesAppendix）· host-agent-loop.mjs system 组装
改法
启动与轮次前读取规则，按 token 预算注入（常驻 ≤800 tok）；.mdc 支持 globs 前置元数据，命中当前编辑文件时追加；超出预算按"优先级 + 最近修改"截断，并在 UI 提示已注入条数。
收益
代码风格、目录约定、禁改区对模型有约束力，直接减少返工。

C9 工具集补齐（决定"能不能做完整项目"）

host-agent-loop.mjs · TOOLS
新增
list_dir / glob（路径发现）· multi_edit（一次多处改）· move_file / delete_file（带确认）· web_fetch（读文档）· todo_write（长任务计划）· shell_start / shell_read / shell_kill（后台进程）· browser_*（复用内置浏览器）。

C10 验证闭环扩展

workspace-run-command.mjs · workspaceRunTests
问题
只认 pytest / npm test，本仓库自己都探测不到（用的是 node scripts/check-*.mjs）。

C11 流式、重试、取消三项执行保障

八、取舍、风险与反模式

三条反模式（不要做）

  1. 不要再写第三套执行环。现有两套已经产生三处行为不一致（去重丢字、400 处理、内容内嵌解析）。正确方向是合并 + 适配器，而不是按通道分叉。
  2. 不要用静态门禁代替端到端验证。17 类脚本全绿、真实链路 5 处断裂，说明"字符串存在"与"功能可用"没有相关性。
  3. 不要用"自动降级到本地"兜底云端失败。这会静默改变模型能力，让用户在不知情的情况下拿到更差的结果，也让日志无法归因。

需要明确的取舍

  • 本地窗口与工具数量的矛盾：4k 窗口下，13 个工具的 schema 就要吃掉 2k。策略是"按任务裁剪工具集"（只读任务只下发 4 个），而不是全量下发。
  • 小模型的计划能力：14B 以下不建议开"多步计划 + 并行子任务"，收益小于噪声；把计划能力留给 ≥14B 或云端。
  • MCP 工具的安全边界：MCP 工具一旦进入执行环，写盘/删库类工具必须走与内置工具相同的权限门（Ask 只读、Plan 暂存），不能因为"来自 MCP"就放行。
