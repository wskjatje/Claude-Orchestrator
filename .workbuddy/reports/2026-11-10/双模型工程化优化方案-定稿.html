一、方案总览与判断

两轮诊断（功能测试 + 代码链路 + 运行实例实测）得到同一个判断：当前的问题不在模型能力，而在执行内核。同一个 14B 模型，在 Cursor 式内核里能完成常规改码；在本项目的内核里，它连第一次读文件都过不去。原因可以压成四个数字：

4,096 tok
Ollama 实际加载窗口。应用按 32,768 算预算，压缩永不触发，首轮即静默截断。
0 个
qwen2.5-coder:14b 返回的原生 tool_calls。调用体在 content 里，执行环看不见。
8 → 0
项目已配 8 个 MCP 服务器，执行环可用 0 个；启用 MCP 还会被门禁禁止回落。
1–2 / 12
当前本地模型在 12 个真实任务上的预估通过数。目标：阶段 C 达到 10–11 / 12。
核心结论 现在要求模型"像 Cursor 一样工作"，等于把 32k 的模型塞进 4k 窗口、把工具调用当普通文本读、把 8 个工具全部丢掉，然后再怪模型不行。这三处修完之前，换任何模型都不会有本质改善；修完之后，14B 级本地模型完成常规任务是可预期的。

方案由三条主线构成，顺序不可颠倒：

  1. 打通（阶段 A）：窗口协商 + 协议降级 + MCP 接入 + 云模型入环 → 从"不能干活"变成"能干活"
  2. 稳定（阶段 B）：读文件、编辑引擎、规则注入、验证闭环 → 从"能干一次"变成"能连续干对"
  3. 对齐（阶段 C）：检查点、仓库地图、计划、路由、可解释 → 从"能用"变成"像 Cursor"

二、问题全景（合并后 9 类）

两轮共记录 21 个具体缺陷，去重后归为 9 类。分类的意义在于：同一类的修法是同一个，按类推进比按缺陷推进少一半返工。

三、目标架构与三项关键决策

3.1 唯一执行内核

当前有两套并行执行环：vendor/cad/local-mcp-orchestrator.js（有 MCP、仅本地、有自己的去重与解析逻辑）和 host-agent-loop.mjs（有云、无 MCP、只有 7 个工具）。两者已经产生三处行为不一致（丢字、400 处理、内容内嵌解析），这正是本轮多数缺陷的来源。

模块职责硬约束
model-adapters.mjs统一消息与工具 schema → 各供应商方言能力（tools / vision / window）来自 resolveModelCapabilities()，禁止猜

edit-engine.mjs所有写盘的唯一入口写前快照、写后校验、失败必回滚
verifier.mjs按项目类型选验证方式验证不通过不得声明完成

迁移策略：先抽取（T01，无行为变更）→ 再逐项接管（T02–T07）→ 最后把 vendor 环降级为 LOCAL_ORCH_LEGACY=1 的回退开关，默认关闭。不做"一次性重写"。

3.2 三项关键决策（ADR）

ADR-1 · 合并执行环，而不是新增第三套
理由：现有两套已证明会漂移（同一模型在两条路径上表现不同）。新增第三套只会让"改一处漏两处"变成"改一处漏三处"。代价是前期 1.5 人日的抽取工作，收益是后续每个需求只改一处。
ADR-2 · 协议降级，而不是绑定某几个"支持 tools 的模型"
理由：实测显示工具调用形态取决于模型 + Ollama 版本 + 模板三者组合，无法用白名单覆盖。三层降级（原生 → 简化 schema → 文本 JSON）能从机制上兜住，且对云端同样适用。代价是需要严格的调用校验（JSON 必须含已知工具名 + 合法参数）。
ADR-3 · 云端失败不自动降级到本地
理由：静默换模型会让用户在不知情下拿到更差结果，也让日志无法归因。改为"明示失败 + 询问是否用本地继续"，并保留已完成的工具轨迹，避免从零重来。

// shared/tool-call-protocol.mjs
export function readToolCalls(message, knownNames) {
  const native = normalizeNative(message?.tool_calls)
  if (native.length) return { calls: native, protocol: 'native' }

  const text = stripFences(String(message?.content || ''))
  for (const obj of balancedJsonObjects(text)) {      // 容错尾逗号、多重调用
    const call = coerceCall(obj, knownNames)          // name 必须在白名单
    if (call) return { calls: [call], protocol: 'content-json' }
  }
  return { calls: [], protocol: 'none' }
}

D. 编辑四级回退（T11 核心片段）

// edit-engine
export function applyEdit(src, oldStr, newStr, opts) {
  let hit = exact(src, oldStr)
  if (!hit) hit = normalized(src, oldStr)      // 空白/换行归一，保留原缩进
  if (!hit) hit = anchored(src, oldStr)        // 首尾行锚点
  if (!hit) hit = fromPatch(src, opts.patch)   // unified diff
  if (!hit) return { ok: false, nearest: nearestSnippets(src, oldStr, 3) }
  return { ok: true, content: hit.apply(newStr) }
}

八、灰度、回滚与风险

灰度策略

  • 按通道灰度：先"仅本地"，再"仅云"，最后"混合"。每个通道保留独立开关（AGENT_RUNTIME_*）。
  • 按用户灰度：设置里提供"新执行内核（Beta）"开关，默认关闭，内部同学先开。
  • 双跑对比：灰度期同一请求可同时记录旧环结果（不写盘），比较工具选择与耗时。

回滚

  • LOCAL_ORCH_LEGACY=1 → 回退到 vendor 环（T00 的修复保留，其余不影响）。
  • 协议层可按模型回退：protocol=legacy-native 只发原生 tools，不做内容解析。
  • 检查点目录自带还原能力，误改可即时恢复。

九、30 分钟见效清单

如果只想先验证判断、再决定投入，按下面顺序做，每项都是分钟级，且不改架构：

  1. 给 Ollama 请求加 options.num_ctx + keep_alive（改动 5 行）——本地模型"忘规则/重复读"会立刻缓解，是最快验证根因的一步。
  2. 删流式去重启发式（T00）——输出不再丢字。
  3. read_file 默认 maxChars 从 16000 降到 4000——单次读取不再撑爆 4k 窗口。
  4. 选择器恒显云模型（T08 最小版）——解开"选不到云模型"的死循环。
  5. HOST_MAX_TURNS 16 → 32——多文件任务的轮次够用。
  6. 启动时校验模型名（对 /api/tags 比对）——消除 qwen2.5-coder:latest not found 这类静默失败。
这 6 项只是"止血" 它们能让本地模型从"完全不能用"变成"偶尔能用"，但不会解决工具协议、MCP、编辑可靠性。正式方案仍按 T01–T21 推进；止血项可作为阶段 A 的第一批提交。
